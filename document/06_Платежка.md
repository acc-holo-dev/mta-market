# 💳 Платежка: полный план подключения (ЮKassa)

> Этот документ — пошаговый план: как подключить приём денег к площадке.
> После подключения этот документ превращается в инструкцию «что и где
> искать, когда что-то не работает».

---

## 1. Что нужно ДО подключения (2 обязательных условия)

1. **Самозанятость или ИП.** Без статуса ЮKassa не подключит выплаты.
   - Самозанятость: 15 минут онлайн (через «Мой налог» или банк).
   - Налог: 4% с физлиц, 6% с юрлиц. Итоговая цифра = ваша цена + налог + комиссия.
2. **Банковский счёт** для выплат продавцам и получения прибыли.

## 2. Регистрация в ЮKassa

| Шаг | Действие | Что получаете |
|---|---|---|
| 1 | Зайти на yookassa.ru, «Подключиться» | доступ в личный кабинет |
| 2 | Выбрать модель: **Маркетплейс** | это ваш случай — деньги идут через вас к продавцам |
| 3 | Заполнить данные самозанятости | статус проверки: 1–3 дня |
| 4 | Дождаться активации | доступ к shopId и секретному ключу |

## 3. Ключевые переменные (получить в личном кабинете ЮKassa)

```
YOOKASSA_SHOP_ID=12345           # ID магазина (Настройки → Магазины)
YOOKASSA_SECRET_KEY=test_xxx     # Секретный ключ (Настройки → API)
YOOKASSA_API_URL=https://api.yookassa.ru
```

**Где искать:** личный кабинет ЮKassa → Настройки → Интегция/API.
Тестовый режим доступен сразу (ключи с префиксом `test_`).

## 4. Схема работы платежа

```
Покупатель → "Оплатить" → Backend создаёт платёж через API ЮKassa
   → Покупатель видит ЮKassa-форму → вводит данные карты
   → ЮKassa присылает webhook (уведомление) на Backend
   → Backend помечает платёж успешным → создаёт лицензию
```

**Критически важно:** статус платежа НЕ определяется фронтендом.
Только webhook подтверждает, что деньги реально пришли.

## 5. Webhooks (уведомления) — что слушать

| Событие | Что делаем |
|---|---|
| `payment.succeeded` | выдать лицензию, начислить escrow |
| `payment.canceled` | откатить корзину, показать ошибку |
| `refund.succeeded` | аннулировать лицензию |

URL для вебхуков: `https://ваш-домен/api/v1/webhooks/yookassa`
Регистрируется: ЮKassa → Настройки → HTTP-уведомления.

## 6. Схема escrow (гаранта) в контексте платежей

```
Покупатель платит 2500₽
   → ЮKassa держит деньги НА СЧЁТЕ ПЛОЩАДКИ (не продавцу!)
   → через 72ч: подтверждение покупателем
   → Backend вызывает выплату продавцу (Минус 15% комиссии)
   → продавцу: 2500 - 375 = 2125₽

Если спор → админ решает: вернуть покупателю / всё равно выплатить.
```

**Реализация в ЮKassa — v2 (по итогам аудита):** статус в PostgreSQL —
это лишь **escrow state machine**, а настоящий escrow должен жить у
платёжного провайдера. У ЮKassa для нашего сценария есть готовые решения:

- **Безопасная сделка (Safe Deal)** — деньги холдируются и выплачиваются
  продавцу после закрытия сделки (ближе всего к нашему замыслу);
- **Split Payments** — платформа распределяет платёж между продавцами
  (классический marketplace).

**Обязательное решение до Stage 4:** выбрать одну модель, изучить
актуальные тарифы/комиссии выплат (в 2026 условия менялись) и строить
DB state machine вокруг реального поведения провайдера. Комиссия
площадки «15%» — не окончательная цифра до сверки с фактурой провайдера.

Также к моделированию обязательны (см. 17_Финансовый_ledger.md):
`provider fee`, `tax/receipt metadata`, `reconciliation`, onboarding
продавцов (identity + payout identity — у ЮKassa продавцы требуют
собственной настройки подключения).

## 7. Подписки (рекуррентные платежи) ⚠️ отложено из MVP

- По итогам аудита подписки перенесены в POST-MVP: renewal, failed
  payment, grace, cancel, reactivation, proration, price changes —
  слишком большой пласт для MVP.
- В MVP — только one-time license (покупка навсегда).
- Когда вернёмся: ЮKassa поддерживает автосписания (без CVV каждый раз);
  первая оплата создаёт `payment_method_id`, Backend запускает списание
  каждый месяц; провал → grace 3 дня → revoke.

## 8. Частые проблемы

| Симптом | Причина | Решение |
|---|---|---|
| Webhook не приходит | не зарегистрирован URL | проверить раздел «HTTP-уведомления» |
| Платёж прошёл, лицензия не появилась | ошибка обработки webhook | смотреть логи Backend |
| Тестовый режим не работает | ключи от продакшена в `.env` | проверить `test_` prefix |

## 9. Команды для разработчика

```bash
# Локально: проверить подключение к ЮKassa (тестовый режим)
curl -X POST https://api.yookassa.ru/v3/payments \
  -u "$SHOP_ID:$SECRET_KEY" \
  -H "Content-Type: application/json" \
  -d @docs/examples/payment_test.json

# Посмотреть статус платежа
# (выполнять после каждой покупки при дебаге)
curl https://api.yookassa.ru/v3/payments/{payment_id} \
  -u "$SHOP_ID:$SECRET_KEY"
```

## 10. Безопасность платежей

- Секретный ключ ЮKassa — только в переменных окружения, никогда в коде
- Проверять подпись/подлинность каждого вебхука
- Не доверять сумме платежа из фронтенда — сверять с ценой в БД
- Логировать все платежные операции (audit_log)
