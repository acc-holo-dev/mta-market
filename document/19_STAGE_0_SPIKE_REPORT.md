# 🧪 STAGE 0 — Отчёт: DRM Feasibility Spike

> **Дата:** февраль 2026 · **Статус: ✅ ПРОЙДЕН**
> Ключевая гипотеза архитектуры подтверждена.

## Вопрос

> «Может ли нативный модуль загрузить зашифрованный Lua payload и
> исполнить его внутри VM вызывающего ресурса — как это делал бы
> защищённый ресурс?»

## Метод

В mta-guard-module добавлена функция модуля `spike_drm_load`
(`source/functions/drm/spike.cpp`):

```
hex payload → hex decode → decrypt → luaL_loadbuffer → lua_pcall
```

Тест `096_drm_spike.lua` гоняет её во встроенном harness — реальный
Lua 5.1 с MTA-патченными заголовками (mock manager, без MTA-сервера).

## Открытия, меняющие продакшен-пайплайн

1. **MTA-формат байткода: 4-байтовый size_t на любой платформе**
   (`SIZE_T_PRECOMPILED_CHUNK` в lundump.c). Офлайн-компилятор
   (Build Tool) ОБЯЗАН использовать MTA-патченный dumper —
   стандартный Lua 5.1 x64 luac даёт «bad header in precompiled chunk».
2. **`string.dump` отключён в рантайме модуля** (`WITH_STRING_DUMP` off):
   покупатель не может сдампить загруженный байткод обратно —
   бесплатно полученный анти-декомпиляционный барьер.
3. Lua C API (`luaL_loadbuffer`, `lua_pcall`) полностью доступен
   модулю — вопрос «влезает ли модуль в lifecycle загрузки ресурса»
   снят: модулю не нужно вмешиваться в loader сервера, достаточно
   функции-регистратора, которую ресурс вызывает сам.
