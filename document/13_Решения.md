# 📜 Журнал решений (ADR — Architecture Decision Records)

> Зачем этот файл: через полгода вы забудете, ПОЧЕМУ выбрали именно так.
> А если захотите переделать — этот журнал покажет, какие ограничения
> вы учитывали изначально, и что могло измениться.
>
> Формат записи:
> **[ДАТА] Решение.** Контекст. → Последствия. Альтернатива, которую отвергли.

---

## ADR-001: TypeScript для Backend, а не Go или Python

**Дата:** февраль 2026
**Решение:** Backend на TypeScript (Node.js).
**Контекст:** проект делается силами одного человека с помощью AI-агента.
**Последствия:** один язык с Frontend, общие типы через packages/shared.
**Альтернатива:** Go — быстрее, но два языка = двойная поддержка.

## ADR-002: Modular monolith, а не микросервисы

**Дата:** февраль 2026
**Решение:** монолит с модулями (auth, licenses, payments...).
**Контекст:** для 1 разработчика микросервисы = избыточная сложность деплоя.
**Последствия:** всё деплоится одной командой. Модульная структура
позволит потом выделить, например, License Server в отдельный сервис.
**Альтернатива:** микросервисы — отвергли, преждевременно.

## ADR-003: Ed25519 + AES-256-GCM (libsodium) для DRM

**Дата:** февраль 2026
**Решение:** только стандартные примитивы, никакого самодельного крипто.
**Последствия:** аудит-безопасно, библиотека libsodium имеет привязки и для C++,
и для Node.js (одинаковые алгоритмы на обеих сторонах).
**Альтернатива:** RSA — отвергли: медленнее, ключи больше.

## ADR-004: Escrow через статус в БД, а не внешние сервисы

**Дата:** февраль 2026
**Решение:** escrow = `purchases.escrow_status` + деньги держатся
в аккаунте ЮKassa площадки.
**Последствия:** простая реализация, но выплаты продавцам идут
через «выплаты» ЮKassa — изучить тарифы при подключении.

## ADR-005: DRM защищает только Lua-скрипты

**Дата:** февраль 2026
**Решение:** модели (DFF/TXD) DRM не шифрует — только watermark.
**Контекст:** движок MTA должен читать ассеты открыто.
**Последствия:** честно фиксируем ограничение; компенсация — Leak Radar.

## ADR-006: Grace period 48 часов

**Дата:** февраль 2026
**Решение:** модуль работает 48ч без связи с License Server.
**Контекст:** баланс между удобством покупателя (не все серверы — 24/7)
и защитой (дольше = проще взломать отключением сети).
**Альтернатива:** 24ч — отклонена: слишком неудобно; 7 дней — слишком небезопасно.

⚠️ **ПЕРЕСМОТРЕНО в ADR-008.**

## ADR-007: Installation keys вместо HWID-identity

**Дата:** февраль 2026 (по итогам внешнего аудита)
**Решение:** identity установки = криптографический keypair (Ed25519),
а НЕ hash(MAC + volume + CPU).
**Контекст:** VM, Docker, cloud-миграции, переустановки ОС ломают
HWID-identity у легитимных клиентов; злоумышленники подделывают.
**Последствия:** hardware-характеристики — только risk-signal
(антифрод), не identity. Переезд на другой сервер не ломает лицензию.
**Альтернатива:** HWID — отвергнут по итогам аудита.

## ADR-008: Lease-модель (24ч) вместо heartbeat+grace

**Дата:** февраль 2026 (по итогам внешнего аудита)
**Решение:** подписанный lease на 24 часа, renew заранее с jitter.
**Контекст:** старая схема (heartbeat 30 мин + grace 48ч) ломала
ресурсы при outage License Server — «всё оплачено, но не работает» =
худший отзыв. Lease действует независимо от связности.
**Последствия:** отзыв действует ≤24ч; 24-часовой outage незаметен
клиенту. Controlled state после 72ч недоступности.
**Альтернатива:** heartbeat — отвергнут (ADR-006 superseded).

## ADR-009: Escrow — реальный механизм провайдера, не статус в БД

**Дата:** февраль 2026 (по итогам внешнего аудита)
**Решение:** статус в PostgreSQL — лишь state machine; реальные деньги —
через ЮKassa Safe Deal ИЛИ Split Payments (выбрать при Stage 4).
**Контекст:** «escrow = статус в БД» — концептуальная ошибка: деньги
должны холдиться у провайдера.
**Последствия:** нужна сверка (reconciliation) с провайдером; продавцы
требуют onboarding у провайдера; комиссия 15% — не окончательная до
сверки с актуальным прайсом.
**Альтернатива:** держать деньги у площадки и платить вручную —
отвергнуто: юридические и операционные риски.

## ADR-010: «Один DLL на всё» отменён → Market Manager

**Дата:** февраль 2026 (по итогам внешнего аудита)
**Решение:** небольшой официальный модуль-менеджер (лицензии,
обновления, rollback) + изолированные ресурсы, как требует архитектура MTA.
**Контекст:** blast radius одного .dll на всё — 1 ошибка = 100 сломанных
ресурсов; MTA-архитектура естественно изолирует ресурсы.
**Альтернатива:** один модуль на всё — отвергнут (v1 README).

## ADR-011: MVP сокращён; DRM spike — Stage 0

**Дата:** февраль 2026 (по итогам внешнего аудита)
**Решение:** из MVP убраны: subscriptions, биржа заказов, чаты, bundle,
промокоды, A/B, seller API, Live Demo, 3D, Leak Radar, депозиты.
До всей разработки — DRM feasibility spike (1–3 дня).
**Контекст:** документация опережала реализацию; исходный scope — ~6
продуктов в одном. Spike доказывает, что C++-модуль может вмешаться в
lifecycle загрузки ресурса MTA — до этого вся архитектура гипотетична.
**Последствия:** MVP scope-based; calendar 5-недель — исправлен на
реалистичный (Stage 0–7). Сроки — приёмкой, не календарём.
**Альтернатива:** писать сразу всё — отвергнуто.

## ADR-012: Финансовый ledger как отдельная структура

**Дата:** февраль 2026 (по итогам внешнего аудита)
**Решение:** immutable `financial_transactions` (append-only, со
storno-корректировками), отдельно от purchases.
**Контекст:** purchase != payment != settlement != payout; старая схема
смешивала их, что делало невозможной честную сверку.
**Последствия:** инвариант Σ transactions == balance; ночная сверка;
reconciliation с ЮKassa ежедневно.
