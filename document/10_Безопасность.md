# 🔐 Безопасность — чек-лист защиты

> Что, от чего и как защищаем. Документ обязателен к прочтению перед
> первым боевым платежом. Отмечайте ✅ по мере реализации.

---

## 1. Аутентификация и сессии

- [ ] Пароли: только argon2id (не md5, не sha256 без соли!)
- [ ] JWT access token TTL 15 мин, refresh TTL 30 дней с ротацией
- [ ] Refresh token — одноразовый: после использования старый отзывается
- [ ] Rate limit на login: 5 попыток / 15 мин / IP
- [ ] 2FA (TOTP) — обязателен для продавцов и админов
- [ ] Сброс пароля: одноразовый токен, TTL 1 час, не раскрывает,
      существует ли email (защита от перебора)

## 2. Платежи (самая опасная зона)

- [ ] Секретный ключ ЮKassa — ТОЛЬКО в переменных окружения
- [ ] Проверка подлинности webhook (IP-allowlist ЮKassa + webhook secret)
- [ ] Idempotency-Key в checkout — защита от двойной оплаты
- [ ] Сумма платежа сверяется с ценой в БД, не с суммой из фронтенда
- [ ] Все операции с деньгами пишутся в audit_log
- [ ] Возвраты — только через админ-панель, с причиной в audit_log

## 3. DRM-модуль

- [ ] Публичный ключ Ed25519 — зашит в бинарник при сборке (не в файле рядом!)
- [ ] Приватный ключ — ТОЛЬКО на License Server (env var)
- [ ] Anti-replay: nonce + timestamp TTL ±30 сек
- [ ] Модуль не пишет ключи в логи ни при каких условиях
- [ ] Проверять целостность выданных DEK (AAD в AES-GCM)

## 4. Инфраструктура

- [ ] HTTPS везде (Cloudflare или certbot), редирект http → https
- [ ] SSH: доступ только по ключу, root-логин запрещён
- [ ] Firewall: открыты ТОЛЬКО порты 80/443 (+SSH с allowlist IP)
- [ ] PostgreSQL и Redis — НЕ доступны извне, только внутри Docker-сети
- [ ] `.env` в `.gitignore` (проверить: `git log --all -- .env`)
- [ ] Автоматические бэкапы БД + проверка восстановления раз в месяц
- [ ] fail2ban или аналог на сервере

## 5. Защита данных пользователей

- [ ] Пароли и токены никогда не логируются
- [ ] HWID и IP — персональные данные: показывать админам только по-делу
- [ ] Экспорт своих данных пользователем (закон о персональных данных)
- [ ] Удаление аккаунта: анонимизация (users → anonymous), не удаление

## 6. Защита от атак (OWASP Top 10 — практический минимум)

| Атака                           | Защита                                                              |
| ------------------------------- | ------------------------------------------------------------------- |
| SQL-инъекции                    | Только параметризованные запросы (ORM/prepared statements)          |
| XSS                             | React экранирует по умолчанию; `dangerouslySetInnerHTML` — запрещён |
| CSRF                            | SameSite cookies для refresh token                                  |
| IDOR (доступ к чужим лицензиям) | Проверка `user_id` на каждом эндпоинте `/me/*`                      |
| Brute-force                     | Rate limit на все POST-эндпоинты                                    |
| Upload exploit                  | Валидация содержимого blob, размер лимит, отдельный S3 bucket       |

## 7. Действия при инциденте (инцидент = утечка/взлом)

```
1. Не паниковать. Зафиксировать время обнаружения.
2. Отключить скомпрометированный доступ (ключи, токены).
3. Отозвать затронутые лицензии (если утечь мог скрипт).
4. Разобрать причину (logs → audit_log).
5. Уведомить затронутых пользователей (честность > страх репутации).
6. Записать постмортем в 13_Решения.md чтобы не повторять.
```

## 8. Золотые правила

1. **Если сомневаетесь — запретить.** Открыть доступ потом всегда проще.
2. **Минимальные привилегии.** У приложения — свой пользователь БД без
   прав на DROP; у админа — отдельный аккаунт, не root.
3. **Логи = золото.** Каждое подозрительное действие должно быть
   восстановимо из audit_log.
4. **Доверяй, но проверяй.** Все внешние данные (webhook, multipart upload,
   API DRM-модуля) — враги, пока не доказано иное.

## 11. Sandbox для загруженных ресурсов (по итогам аудита) ⭐

Smoke-тест = **исполнение чужого загруженного кода на нашей
инфраструктуре**. MTA-ресурсы содержат скрипты и имеют права сервера —
MTA Wiki прямо рекомендует проверять meta.xml, source, ACL и
происхождение ресурса. Поэтому:

- Динамическое исполнение — **только в эфемерном sandbox**:
  - disposable container/VM, non-root, без host mounts;
  - CPU/RAM/PID limits, network restrictions, fs restrictions, timeout;
- Разделить **static validation** (структура, meta.xml, размер,
  mime-check, archive bomb protection — всегда) и **dynamic execution**
  (только для approved ресурсов);
- Запрещать по правилам площадки: ресурсы, требующие админ-прав,
  скрытые external downloaders, загрузку исполняемого кода в рантайме,
  обфусцированный Lua без disclosure, автоматическую модификацию ACL,
  «phoning home» на неизвестные домены.

## 12. Усиления, добавленные по итогам аудита

- [ ] **JWT storage:** refresh token — httpOnly Secure cookie, не
      localStorage; refresh token family + reuse detection; таблица
      devices/sessions; logout all
- [ ] **RBAC:** не просто user/seller/admin, а roles + permissions
      (admin ≠ может делать refund; support ≠ видит HWID/IP;
      finance ≠ может отзывать лицензии)
- [ ] **Ключи:** versioning + ротация (key_id), revocation list,
      разделение dev/prod ключей, план замены при компрометации
- [ ] **Recovery codes для 2FA** (иначе потерял телефон — потерял аккаунт)
- [ ] **Upload hardening:** archive bomb protection, MIME sniffing,
      лимит размеров распаковки, запрет SVG/script upload, image
      decompression limits
- [ ] **Supply chain:** dependency scanning, container image scanning
- [ ] **Disaster recovery:** RPO/RTO определить, offsite + зашифрованные
      бэкапы, восстановление signing keys отдельно от БД (потеря
      signing key хуже потери БД!)
- [ ] **Не git push main → production:** CI → migration check →
      staging → smoke → approval → production; миграции forward-compatible
