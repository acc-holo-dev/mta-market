# 🛡️ Спецификация DRM — защита скриптов

> Сердце площадки: как скрипты шифруются, продаются, защищаются.
> Документ описывает протокол взаимодействия DRM-модуля (C++) с License Server.
> **v2 — переработано по итогам внешнего аудита:** installation keys вместо
> HWID-identity, lease-модель, key rotation, честная формулировка защиты.

---

## 0. Честная формулировка защиты (принципиально)

DRM **не гарантирует** «скрипт невозможно украсть». Покупатель — владелец
сервера, он контролирует машину; plaintext неизбежно появляется в памяти.

Правильная формулировка продукта:

> **«Массовое копирование существенно усложнено, лицензии контролируются,
> незаконные копии можно атрибутировать с высокой достоверностью».**

Это стандартный и честный DRM-подход (см. MTA Wiki: Script security —
compiled scripts лишь повышают сложность анализа, не создают абсолютной
защиты).

## 1. Участники

| Компонент | Язык | Где живёт | Роль |
|---|---|---|---|
| Market Manager (DRM-модуль) | C++ (на базе mta-sdk-module) | MTA-сервер покупателя | Расшифровывает, проверяет, отключает |
| License Server | часть Backend (логически выделен) | VDS площадки | Подписывает leases, отзывает |
| Build Tool | Node.js CLI | сервер площадки | Шифрует и упаковывает скрипты продавца |

## 2. Криптографические примитивы

| Задача | Алгоритм | Ключ |
|---|---|---|
| Подпись токена лицензии | Ed25519 (libsodium) | приватный: License Server; публичный: зашит в модуль |
| Шифрование скрипта | AES-256-GCM | DEK (Data Encryption Key) |
| Обёртка DEK | AES-256-GCM | ключ из `HKDF(license_key_id + installation_secret)` |
| Anti-replay | nonce (16 байт) + timestamp + TTL | — |
| **Ротация ключей** | `key_id` в токене | модуль проверяет список валидных публичных ключей |

**Ротация ключей подписи:** каждый подписанный токен содержит `key_id`.
Модуль умеет проверять несколько публичных ключей (active + previous),
что позволяет ротировать приватный ключ без мгновенного обновления
всех установленных модулей.

## 3. Identity: installation keys, НЕ HWID ⭐

**v1 (отвергнуто аудитом):** `HWID = hash(MAC + volume + CPU)` как identity.
Проблемы: VM, Docker, смена адаптера, cloud-миграции, backup/restore,
различия Windows/Linux — легитимные клиенты ломаются, злоумышленники
подделывают.

**v2 (текущая модель):**

```
license
    ↓
installation (1..N, лимит настраивается)
    ↓
installation_id (random) + installation keypair (Ed25519)
```

- При первой активации модуль **генерирует keypair**;
- Backend знает: `license_id`, `installation_id`, `public_key`;
- При каждом verify сервер шлёт **challenge**, модуль доказывает владение
  private key подписью (challenge/response);
- Секрет никогда не покидает сервер покупателя и не зависит от железа.

```
Identity = cryptographic installation key
MAC / CPU / disk = опциональная telemetry, risk-signal (не identity!)
```

Замена ironа/переезд VPS теперь не ломает лицензию; подозрительные
паттерны (5 разных «желез» на один installation_id за сутки) —
flag в антифрод, а не ban.

## 4. Lease-модель вместо heartbeat+grace ⭐

**v1 (отвергнуто):** heartbeat каждые 30 мин + grace 48ч.
Проблема: «всё оплачено, License Server лежит, ресурс встал» = худший
отзыв в жизни площадки.

**v2 (текущая модель):**

```
license lease = 24 часа (подписанный Ed25519 токен с key_id)
```

- Модуль может **запрашивать новый lease заранее** (за 4 часа до
  истечения, с рандомизированным jitter);
- Lease действует 24ч независимо от связности: короткий outage
  License Server вообще ничего не ломает;
- Стратегия при недоступности:
  - lease ещё жив → работаем;
  - lease истёк + сервер недоступен > N раз → warning в лог;
  - lease истёк + недоступность длится > 72ч → controlled state
    (скрипт останавливается с внятным сообщением);
- Lease содержит `key_id`, `expires_at`, список ресурсов и wrapped DEK.

Состояния license lease: `active → expiring_soon → expired → revoked`.
Revocation проверяется при каждом renew — отзыв действует максимум 24ч.

## 5. Жизненный цикл скрипта

### 5.1 Продавец публикует
```
1. Upload → Backend проверяет ресурс (валидация zip, статический анализ)
2. Build Tool Backend'а:
   a. luac_bytecode = компиляция Lua
   b. DEK = random 32 bytes
   c. blob = AES-GCM(bytecode, DEK)       → S3
   d. wrap = AES-GCM(DEK, server_secret)  → таблица (не в blob!)
```

### 5.2 Покупатель активирует
```
1. POST /v1/activate { license_key, installation_pubkey }
   (модуль сгенерировал keypair при первом запуске)
2. License Server: лицензия активна? installations < лимита?
3. YES → создаётся installation, выдаётся первый lease
4. Модуль проверяет Ed25519-подпись lease (публичный ключ зашит в .dll)

Пока lease не получен, decrypt(blob) невозможен:
нет DEK → нет расшифровки → скрипт не работает.
```

### 5.3 Verify (renew lease)
```
POST /v1/verify { installation_id, challenge_sig, nonce, resources }
→ { lease (signed), deks: {resource: wrapped_DEK}, sig }
```
- Отвечённый `wrapped_DEK` расшифровывается ключом, выведенным из
  `installation_secret` — украденный ответ не работает на другой установке.

### 5.4 Обновление скрипта
```
1. Продавец публикует новую версию (channel: stable/beta)
2. Покупатель видит changelog и жмёт "Обновить"
3. Модуль скачивает новый blob, СТАРАЯ ВЕРСИЯ СОХРАНЯЕТСЯ
4. Rollback в кабинете одной кнопкой
```

## 6. Что модуль делает в C++ (и что НЕ попадает в Lua)

**Модуль НЕ отдаёт в Lua:** ключи (DEK, KDF), функцию расшифровки.

**Модуль отдаёт в Lua:** `license_check(resource_name) → boolean` —
Lua лишь узнаёт «лицензия активна», но обойти не может (реальное
исполнение расшифрованного кода всё равно требует модуля).

## 7. DRM Spike (Stage 0 — до всей разработки!) ⭐

**Ключевой вывод аудита:** архитектурное утверждение «модуль сможет
загрузить зашифрованный ресурс в VM ресурса MTA как нам нужно» —
**не доказано**. MTA загружает ресурсы через внутренний loader
(`LuaLoadBuffer`), а модули — это `<module>` в mtaserver.conf, что не
автоматически даёт «новый защищённый resource loader».

Поэтому первым делом (1–3 дня):

```
encrypted test.lua → C++ module → AES-GCM decrypt →
Lua execution → ресурс нормально работает
```

Проверить минимум на: Windows + Linux, MTA 1.6.x. **Только после
успешного spike** строить настоящий DRM. Если spike провалится — вся
концепция площадки нуждается в пересмотре до написания остальных частей.

## 8. Сборка модуля

- Форк `mta-sdk-module`, добавляются папки:
  `source/sdk/license/`, `source/sdk/license/crypto/`
- Сборка: `cmake --preset win-mingw` (.dll) и `linux-gcc` (.so) — оба
  артефакта публикуются на площадке.
- Публичные ключи Ed25519 (список, с учётом ротации) зашиваются при сборке —
  продакшен и dev используют разные наборы.

## 9. Модель угроз (что защищаем и от чего)

| Угроза | Защита |
|---|---|
| Покупатель копирует файл скрипта | Бесполезно: blob без DEK не расшифровать |
| Перенос на другой сервер | installation keypair: lease и DEK привязаны к установке |
| Подделка `license_check()` | Реальное исполнение — в C++ |
| Подмена DNS / фейковый License Server | Модуль требует Ed25519-подпись (ключ зашит) |
| Replay старого lease | nonce + timestamp TTL + короткий срок lease (24ч) |
| Перехват трафика | TLS + подпись поверх payload |
| Слив через модификацию модуля | Watermark в каждой копии + forensic scoring |
| Outage License Server | Lease-модель: 24h безболезненно, потом controlled state |

## 10. Что DRM НЕ защищает (важно понимать)

- **Модели (DFF/TXD)** — движок читает их открыто; защита = watermark + forensic.
- **Память MTA-сервера** — plaintext неизбежно оказывается в памяти.
- **Реверс-инженерия** — C++ усложняет, но не исключает. Компенсация:
  watermarks, lease-отзыв, юридическая работа.
